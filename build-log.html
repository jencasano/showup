Field notes System characteristics worth knowing ▾
  • Events accumulate indefinitely
    events/{uid}/items has no TTL and no auto-prune. Roughly 4-6 docs per active user per day (one per burst, one per diary entry). Viewer reads stay flat because WINDOW_DAYS in event-read.js caps the query to the last 30 days, but Firestore storage grows linearly forever. If this becomes a concern: shorten the read window, add a Firestore TTL policy on the events collection, or compact older events into monthly summary docs. Nothing needed at current scale.
  • Activity photos (proof-of-habit)
    User feedback (Neithan): ability to attach a photo when logging an activity, like Forfeit or BeReal-style proof. Different from diary photos -- diary is reflective ("how was today"), activity photos are documentation ("I did the thing"). Key design tension: the single-tap logging mechanic is sacred, photos must be optional and zero-friction. Best candidate surface is the mobile Day Sheet (camera icon per habit row), with desktop capture deferred since there's no day detail popover yet. Needs: new Firestore path (photos per activity per day), upload flow, viewing UI (per-activity photo reel), and a clear answer on how it coexists with diary photos. Bigger than it looks -- parking for now.

Diary Phase B: Diary Tab

A dedicated diary tab joins the main navigation -- sidebar on desktop, bottom nav on mobile -- replacing the old 'diary' action button that only popped a modal. The tab is a personal reading room with three stacked sections: a notebook hero with a 'write today's page' CTA, a 'this month's pages' grid showing every day from 1 through today, and a bookshelf at the bottom with notebook spines for each past month that has diary entries. Saving an entry updates the affected page card, fill bar, hero subtitle, and notebook stat in place via a new 'diary:saved' event -- no full re-render.

Tab routing
The sidebar and bottom-nav diary buttons switch from data-action='diary' (which used to fire a one-off openDiaryFromNav helper that just opened the mobile sheet) to data-tab='diary'. A new #tab-diary panel joins #tab-mylog / #tab-following / #tab-all inside #app-content. switchTab() now treats diary as a real tab: hides the month bar (same as following / all), toggles the panel display, and routes loadActiveTab to a new loadDiaryTab(yearMonth, container, user) in js/tracker-diary-tab.js.
Notebook hero + CTA
Section 1 reuses renderDiaryNotebook for the closed-book widget and adds a viewport-aware onOpen callback so the notebook opens the desktop modal on wide screens and the mobile sheet on phones (the existing hard-coded openDiaryModal call now falls back when no callback is passed, so mylog is unchanged). The hero text block reads 'your diary.' in Fraunces italic with a 'May 2026: N pages filled so far. keep going.' subtitle and a solid-red 'write today's page' button. Mobile centers the notebook above the text and scales the cover's internals down (title 2.5rem -> 1.4rem, stat strong 3rem -> 1.6rem, spine 26px -> 18px, etc.) so the small 140x190 book doesn't overflow.
This month's pages grid
Section 2 has a section header ('this month's pages' / month label), a fill bar ('X of Y' + yellow track + percentage), and a 5-column desktop / 4-column mobile grid of mini page cards. Reuses the .diary-mini-page class family from the existing pages modal. Filled cards get a dotted-paper background, yellow-tinted border, note preview in Caveat, polaroid photo thumbnail, and an amber dot in the corner. Today's card gets the coral border ring. Empty cards render with faint ruled lines and are clickable too -- tapping any past or current day opens the diary modal/sheet at that day so the user can write or read.
Past months bookshelf
Section 3 scans back from the current month, parallel-fetching getDiaryDays + getMonthCover per month, stopping after 12 months or 3 consecutive empties. Each month with entries becomes a vertical book spine on a wooden plank: spine background is the month's coverGradient, with leather cross-hatch texture, top highlight + bottom shadow bands, a slight asymmetric border-radius, two decorative dots, the abbreviated month label rotated vertically via writing-mode, and the entry count at the bottom. Size variants by entry count: 20+ entries get h-tall + w-thick, 10-19 get h-medium, under 10 get h-short + w-thin. Light covers (Quiet cream) switch text to dark. Books lean -0.8/0.5/-0.3deg per nth-child. Hover lifts and rotates with a tooltip showing the full month name and fill count. Tapping opens the mobile sheet in pages view on phones, the desktop pages modal otherwise.
Surgical save updates
saveDiaryEntry now dispatches a window 'diary:saved' CustomEvent with the userId, yearMonth, and day. The diary tab attaches a per-render listener (with an AbortController so re-renders cleanly replace it) that, when the tab is visible and the event matches, does two things. First it suppresses the reopen-the-diary-modal chain that tracker-diary's onSaved callbacks fire by yanking all diary overlays out of the DOM and watching for new ones for ~800ms (MutationObserver runs before paint so there's no flicker). Second it re-fetches the affected entry and surgically updates that single page card plus the fill bar / hero subtitle / notebook stat. No container.innerHTML wipe, no Firestore re-scan of the rest of the month.
Empty-page parity + saved-day landing
Tangential cleanup that shipped alongside the tab. Empty diary pages in both the desktop modal and the mobile sheet now mirror the filled-state layout: same left-aligned date treatment, same activity chips row, with 'this page is blank...' text + three ruled lines replacing the note/photo and a solid-red 'write something' button matching the 'Edit entry' style. (Previously the desktop empty state used .quiet-room from My Log, which dragged in unrelated sparkle motifs + a centered layout.) After save from the mylog notebook, the reopened diary modal lands on the day you just wrote and the calendar's dot for that day appears immediately -- onSaved now passes the saved day as initialDay and mutates the diaryDays Set in place so the rebuilt calendar reflects it without a re-fetch.
Shelf design tokens
Four new tokens in both Side A and Side B blocks in css/variables.css: --shelf-bg, --shelf-top, --shelf-shadow, --shelf-wall. Side A is warm tan with a soft amber wash; Side B is dark mahogany with deeper shadow. The bookshelf surface, plank back-wall, and shadow all read from these, so the whole shelf adapts to theme without component-level overrides.

May 25, 2026 Shipped FO07
Feed: Perfect Week Milestone

A new signal context that recognizes when every activity hit its cadence target for a complete Monday-to-Sunday week. Harder than a streak (which just means "something logged each day") because it requires every individual target to be met. Earns the milestone card treatment (warm wash, gold stripe, glowing badge). The computation lives in a new module (js/signal-week.js) to keep following-signals.js focused on cascade logic.

New module: js/signal-week.js
Exports checkPerfectWeek(logEntry, yearMonth, referenceDate). Determines the most recently completed Mon-Sun week, checks that it falls entirely within the current yearMonth, then verifies every activity's mark count meets or exceeds its cadence target for that week. Returns a boolean. 40 lines, single responsibility, no side effects.
Signal cascade integration
perfect_week slots between streak_15 and streak_7 in the priority order inside computeSignal() in following-signals.js. A 15-day streak is a bigger deal than a single perfect week, but a perfect week is harder than a 7-day streak because it requires every target met, not just presence. If both perfect_week and streak_15 apply, streak_15 wins.
Milestone treatment
perfect_week added to MILESTONE_CONTEXTS and MILESTONE_LABELS in feed-event.js. Badge label: 'perfect week'. Gets the full milestone visual treatment: warm wash, gold top stripe, glowing badge with shimmer animation. Ghost cards get the reduced treatment.
Copy variants
Ten new copy templates added to signal-copy.json. Sharing (4 variants) celebrates completeness: 'hit every target this week.' Low key (3 variants) keeps it abstract: 'had a perfect week. Quietly.' Ghost (3 variants) stays closed-door: 'every target met. Quietly.' The tone distinction: streak copy celebrates consistency, perfect week copy celebrates completeness.
Design decisions
Perfect week fires on the log that completes the week, not retroactively. Cross-month weeks are not evaluated (Monday must fall within the current month). Only the most recently completed Mon-Sun week is checked, not historical weeks. The check runs at burst write time via computeSignal(), so the contextKey is locked into the event doc for all viewers.

Milestone card visual treatment
Feed cards for milestone contexts (first_ever, comeback_big, comeback_small, streak_7, streak_15, streak_25, streak_full_month) now render with a three-layer visual treatment: a warm yellow background wash, a thin gold gradient stripe across the top edge, and a glowing milestone badge that replaces the tier badge. Setup events are not milestones. Mid-month re-setup is silent. Setup copy is abstract (no activity names revealed). Milestone treatment only applies to log events, not diary or setup. streak_3 is too early to celebrate. The milestone badge replaces the tier badge rather than augmenting it, keeping the card header clean.

Polish · Past-month lock

Activity logging is now read-only for past months. The current month stays fully open for backfill (forgot Tuesday? fill it in on Saturday), but once the month turns, the calendar is sealed. Diary remains writable for all months -- it's a journal, not a scorecard. The lock is visual and behavioral: past-month grids render at reduced opacity with no tap/hover affordances, a quiet DM Mono line appears near the month heading with a randomly picked copy variant, and the Manage Activities gear icon hides entirely. No toast interruptions, no error states, just a settled page that makes it obvious the chapter is closed.

Day tap lock, desktop and mobile
Both js/tracker-mylog.js (desktop grid) and js/cal-card.js (mobile calendar) suppress day toggles when the active yearMonth is earlier than the current year-month. Click handlers are removed entirely rather than guarded with a toast -- the visual treatment communicates the lock, so tapping into silence is the right UX. Mobile day sheet also respects the lock.
Visual muting
Past-month calendar grids render at reduced opacity so the whole surface reads as settled rather than active. Logged markers stay visible for history browsing, but the grid loses its pointer cursor and hover highlights. The effect is subtle -- enough to feel different, not enough to feel disabled.
Persistent copy note
A small DM Mono line in var(--ink-faint) appears near the month heading when viewing a past month. Randomly picked from a pool of five variants on each render: 'that chapter's closed.' / 'in the books.' / 'done. locked.' / 'this month is sealed.' / 'you showed up (or didn't).' Copy pool is shared between desktop and mobile so both draw from the same list. No toast, no icon, no box -- just a quiet line that's part of the page.
Manage Activities gear hidden
The gear icon on the calendar card badge is suppressed when viewing a past month. Activities for closed months are not editable.
Diary stays open
Diary entries remain fully writable for past months. No muting, no lock, no note on the diary surface. The diary is a journal -- you might want to write about a memory from last month, and the app should never stop you.
Design decision: honor system for the current month
The lock only applies at the month boundary, not per-day. Users can backfill any day within the current month, same as filling in a paper journal the morning after. The app trusts you to be honest with yourself. Past months close because historical data feeds streaks, milestones, and eventually social features -- that data needs to be trustworthy.

May 23, 2026 Shipped FO05
Feed · Per-Burst Cards + Events Persistence

Two changes that together turn the feed from a presentation-only projection into a real chronological timeline. First, each debounce burst became its own permanent card instead of overwriting the day's existing one (event key switched from {uid}-log-{dateStr} to {uid}-log-{batchId}). Then, the whole event identity moved out of viewer memory into Firestore. Bursts and diary entries are now first-class documents at events/{uid}/items, written once by the author when the debounce closes, read by every follower from the same source. Refresh no longer collapses multi-burst history, and every viewer sees the same cards in the same order. Same model leaves room to add user-written posts, likes, comments, and permalinks later without another schema change.

Per-burst event key
Event key went from {uid}-log-{dateStr} (one card per person per day, later writes silently replaced the earlier card) to {uid}-log-{batchId}, where batchId is the epoch millis of the first mark in the debounce burst. Same burst always produces the same key; later bursts produce new keys, so two sittings the same day land as two separate cards. buildLogEvent gained a burst opts arg; tracker-following.js gained a per-uid knownMarks diff so it can identify which marks belong to the just-fired burst vs. earlier history. burstActivities (only the activities logged in this burst) flows through to the renderer for the action line, while computeSignal still sees the full month's marks for streak/comeback context.
spec
Follow-up bursts lock to default copy
First card of the day can still earn comeback/streak copy, but subsequent bursts that day land on default copy. Without the lock, computeSignal kept returning "comeback" for every burst on the same day, since the only-active-day-is-today + prevActiveDate-months-ago conditions stay true no matter how many times you've logged. Fix locks contextKey on the card at fire/write time: if any earlier card already exists for this uid + dateStr, stamp lockedContext = "default" so the renderer skips re-evaluating. The comeback moment gets claimed exactly once.
Copy variants vary per burst
Two default cards from the same person on the same day were always picking the same template (e.g. both "{firstName} marked {activities}. Done.") because pickCopy seeded on uid + dateStr -- a stable seed per person per day. Threaded an optional extra seed component through resolveFeedCopy and passed event.batchId at render time, so each burst rolls its own variant from the four-template default pool.
Events promoted to first-class documents
Bursts and diary entries now live at events/{uid}/items/{eventId} in Firestore. Author writes once when the debounce closes (or when a diary entry is saved); every follower reads the same doc via onSnapshot. Replaces the previous viewer-side knownMarks diff, which produced cards that only existed in memory and vanished on refresh. Deterministic doc IDs (burst-{batchId}, diary-{dateStr}) make writes idempotent; events are immutable history (no delete, no edit on bursts). contextKey is computed at write time using the author's full log + user meta, including the subsequent-burst default-copy lock, so the card looks the same to every viewer.
spec
Two-mode migration, no data move
Existing users have log/diary docs but no events. The viewer subscribes to the events collection per followed user alongside the existing log/diary listeners. If events exist for a uid, the events listener becomes authoritative and any previously-synthesized log cards are purged. If the events collection is empty, the legacy projection stays active as fallback (one historical card per person, same as before). New writes always go through events, so the cutover is gradual and lossless -- no backfill required.
Modular split, two new files
js/event-write.js holds the author-side write path: recordBurstMark (debounced, flushes on quiet window close), recordBurstUnmark (cancels a still-pending entry), recordDiaryEvent (immediate on save, sets editedAt on subsequent saves). js/event-read.js holds the viewer-side subscribeToUserEvents listener that windows on the last 30 days and normalizes Firestore docs into the shape the renderer already expects. tracker-following.js gained one new field (eventsUnsubMap) and two handlers (onEventDoc, onEventDocRemoved); the existing onFeedEvent grew a single early-return guard so the new and legacy paths never both fire for the same uid.
Firestore note: what you see
New top-level collection: events. Structure is events/{uid}/items/{eventId}. The {uid} doc itself is empty (Firestore shows it greyed out with "this document does not exist") -- click in to see the items subcollection, which holds the actual event docs. Doc IDs are deterministic: burst-{epochMs} per burst, diary-{YYYY-MM-DD} per diary entry. Volume is roughly 4-6 docs per active user per day; events accumulate indefinitely (no TTL) but the viewer query only reads the last 30 days. Rules in firestore.rules: any logged-in user can read (privacy still enforced client-side), owner-only create, diary updates allowed for editedAt, nothing can delete -- events are history.
What this unlocks
User-written posts (type: "post" with a text field), milestones, likes/reactions (subcollection on the event), comments, notifications, permalinks, and a Twitter-style fan-out timeline if follow counts ever scale -- all build on this collection without a schema migration. The same events doc shape is the substrate. Closes the "feed is observer-relative" problem flagged at the end of FO04.

Polish · Color audit

Three related deck items (#21 no-full-weeks calendar preview readability on Side A, #22 progress + stats color audit, #23 full-week calendar theme polish) shipped together since they share the same root cause. Dozens of hard-coded Tailwind hex values (#22C55E green-500, #F59E0B amber-500, #EF4444 red-500, #15803d, #0e7490, #4338ca, #fb923c, #86efac, etc.) bypassed the Mixtape token system, leaving Side B half-broken (badge backgrounds stayed unchanged across themes, only text color got a one-off override) and the My Progress card writing inline styles directly from JS. The done banner pill referenced var(--color-success) which was never declared, so the fallback #22C55E always fired. The fw-empty-overlay used a dark navy backdrop on both themes, looking like a bruise on Side A cream. Three rounds of cleanup: new semantic tokens in variables.css, every consumer-facing rule rewritten to use them, and the inline JS color logic replaced with class-based assignment so the cascade stays in CSS where it belongs.

New semantic tokens, three tiers + five paces + overlay
css/variables.css gains a status-tier system (--status-hit/caution/miss with matching -wash and -border opacity ramps) shared across progress bar fills, fw-badges, fw-dots, summary-week-chips, and status pills. Five pace tokens (--pace-ahead/ontrack/behind/early/started, also with washes and borders) drive the pace badge row. --bar-hit/caution/miss alias the status tiers so the JS-applied fill classes resolve through one indirection. --fw-overlay holds the cream-frosted-glass value on Side A (rgba(244, 236, 216, 0.88)) and a maroon-frosted-glass value on Side B (rgba(42, 21, 24, 0.88)). Side A status-caution is #B8860B (a darkened gold) rather than --yellow #E8B33A directly, since --yellow reads too bright against cream for fills and text; on Side B --yellow works fine against the dark maroon so it's used directly. Every other token derives from existing palette colors (--green, --blue, --red, --paper). No new hex introduced beyond that one B8860B exception.
spec
Pace badges, all five states, no more side-b text overrides
.pace-badge--ahead/on-track/behind/early/started each replaced their three hard-coded values (color/background/border) with var(--pace-*) references. The five [data-theme="side-b"] text-color one-offs (#4ade80, #67e8f9, #f87171, #a5b4fc, #5eead4) are gone since the tokens auto-resolve per theme. Ahead and started now share the green family on both sides; on-track and early share the blue family on Side A and consolidate to teal on Side B (since Side B's --blue is teal); behind shares the red family on both sides.
FW badges, dots, and legend share status tokens
.fw-badge--hit/close/miss and .fw-dot--hit/close/miss now reference --status-hit/caution/miss tokens, the same ones the progress bar fills use, so the three-tier color system is consistent everywhere a "did you hit, get close, or miss" reads on screen. .summary-week-chip--hit/miss (currently dead code, retained for future use) also migrated to the same tokens.
Status pills split into "to go" and "met"
.summary-habit-streak was a single class doing two jobs: orange "X to go" pill and a green "Target met" pill that hijacked the same styling. The base rule lost its hard-coded orange (#fb923c on rgba(249, 115, 22, ...) wash and border) and now carries only layout. Two new variant classes carry the color: .summary-habit-streak--togo uses the --status-caution token family (gold on cream, yellow on maroon) and .summary-habit-streak--met uses --status-hit (forest green on cream, teal on maroon). tracker-summary.js writes the right variant directly into the markup so the cascade decides the color, no inline style needed. The old [data-theme="light"] orange override on .summary-habit-streak deleted since it described a class that no longer carries color directly.
Progress bar fills + pct text move from inline styles to classes
tracker-summary.js used to compute a barColor hex string in JS and apply it twice via inline style="background:..." on the fill div and style="color:..." on the pct span. That bypassed CSS entirely, so the design system had no hook to control the bar color per theme. The barColor variable is gone; in its place a tier string ("hit"/"caution"/"miss") drives class assignment: .summary-habit-fill--hit/caution/miss for the bar fill (only width stays inline) and .summary-habit-pct--hit/caution/miss for the pct text. The over-target case keeps the existing .summary-habit-pct--over class which now also resolves to --status-hit. Three new fill classes added to tracker.css that read --bar-hit/caution/miss. The phantom var(--color-success, #22C55E) / var(--color-warning, #F59E0B) / var(--color-danger, #EF4444) references both in JS and CSS are removed; var(--color-success) was never declared anywhere in variables.css so the fallback always fired.
Over-target glow simplified, done banner pill uses a real token
.summary-habit-pct--over dropped its #86efac color, the rgba(34, 197, 94, 0.35) text-shadow glow, the secondary 0 0 2px rgba(134, 239, 172, 0.55) sparkle, and the saturate(1.08) filter. The glow effect was a Tailwind-era visual that does not fit the Mixtape editorial aesthetic, where the visual emphasis comes from typography and color, not lit-up text. Now it's a clean color: var(--status-hit). The transition list on .summary-habit-pct trimmed accordingly (was color/text-shadow/filter, now just color). The done banner pill background switched from var(--color-success, #22C55E) to var(--status-hit), so the "All done!" pill now reads dark forest green on Side A cream and teal on Side B maroon instead of the bright Tailwind green-500 on both.
FW empty overlay, frosted glass per theme
.fw-empty-overlay swapped its rgba(30, 35, 60, 0.75) dark-navy backdrop for var(--fw-overlay), which resolves to cream-frosted glass on Side A and maroon-frosted glass on Side B. The h4 and p text colors moved off var(--text-primary) (a token that was never declared) and var(--text-muted) onto var(--ink) and var(--ink-soft) directly, which auto-swap and stay readable on both backdrops. The existing [data-theme="light"] override that switched the backdrop to white-ish never fired (the active theme is "side-a", not "light") so it was deleted as dead code. Opacity tuned down from the initial 0.88 to 0.72 with a 1px backdrop blur (formerly an inconsistent 0px on the standard property and 3px on the webkit one), so the calendar grid behind the overlay reads as a soft suggestion of structure rather than disappearing completely. Closes deck item #21 (no-full-weeks preview calendar readability on Side A) since the same overlay drives both the My Progress card empty state and the closed diary card preview.
Activity cadence tag uses the blue family
.activity-cad-tag was running on a hard-coded indigo (rgba(99, 102, 241, ...)) for the dark-theme treatment plus a [data-theme="light"] override with #4338ca text. Both gone; the rule now uses color: var(--blue) with color-mix(in srgb, var(--blue) 14%, transparent) for the wash and 28% for the border. On Side A that resolves to the slate-blue #4F6C8E, on Side B to the teal #5EAAA8, both readable on their respective papers without any theme override on the rule itself.
[data-theme="light"] cleanup, fourteen blocks renamed or removed

One selector block for WebKit/Blink, two new properties on the existing html rule for Firefox, done.

Token mapping, three parts, zero new custom properties
Track resolves to var(--paper-edge), which is #DCCFA6 warm tan on Side A and #3A1D20 deep maroon on Side B. Thumb resolves to var(--ink-faint): #9C8874 muted brown on Side A, #6E504B muted rose on Side B. Thumb hover resolves to var(--ink-soft): #5A463A dark brown on Side A, #B18A84 dusty pink on Side B. spec
WebKit pseudo-elements with a floating thumb
::-webkit-scrollbar is 8px wide, thin enough to be discreet and wide enough to grab on a trackpad or touchscreen. ::-webkit-scrollbar-track paints the track background. ::-webkit-scrollbar-thumb uses a fully rounded 9999px radius plus a 2px solid transparent border and background-clip: padding-box, which is the standard trick for making the thumb appear to float inside the track with a small air-gap on both sides instead of filling edge-to-edge. ::-webkit-scrollbar-thumb:hover swaps to the hover token so the thumb darkens slightly when you grab it. Covers Chrome, Safari, and the current Blink-based Edge.
Firefox via scrollbar-width + scrollbar-color
Firefox doesn't support ::-webkit-scrollbar pseudo-elements, so it uses a different mechanism: scrollbar-width (auto, thin, none) and scrollbar-color (two colors, thumb first, track second). Both properties land on the existing html rule in base.css alongside overflow-y: scroll. scrollbar-width: thin matches the 8px WebKit sizing close enough; scrollbar-color: var(--ink-faint) var(--paper-edge) wires into the same tokens. Firefox doesn't support hover states or border-radius on scrollbar thumbs via these properties, which is fine; the spec explicitly accepts the reduced treatment rather than trying to ship a polyfill.
No data-theme override needed
This is the point of the round. Because every part of the scrollbar resolves to a token that already auto-swaps via [data-theme="side-b"] in variables.css, the scrollbar rules themselves can stay theme-agnostic. One block of CSS handles both themes. Toggling between Side A and Side B recolors the scrollbar instantly with no flash, no layout shift, and no additional selectors. A minor detail that would have been three selectors' worth of duplication without the token discipline established in the earlier Mixtape passes.
